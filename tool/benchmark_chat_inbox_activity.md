# Chat inbox derived activity benchmark

Build `tool/benchmark_chat_inbox_activity.dart` with `flutter build macos --profile --no-pub --target tool/benchmark_chat_inbox_activity.dart`. Launch `build/macos/Build/Products/Profile/Discourse.app/Contents/MacOS/Discourse` directly. It prints a `CHAT_INBOX_ACTIVITY_REPORT` JSON line and exits nonzero on an incorrect output, missing callback, or unexpected Store write count.

If local provisioning prevents that benchmark build, build the generated workspace with `xcodebuild -workspace macos/Runner.xcworkspace -scheme Runner -configuration Profile -derivedDataPath build/macos -destination platform=macOS -quiet CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO ARCHS=arm64 ONLY_ACTIVE_ARCH=YES build`. Keep application signing configuration unchanged.

Use the same harness on each exact source revision. Run at least five alternating baseline/candidate processes in the shared validation lane. Disable CPU sampling in timing processes with `FLUTTER_ENGINE_SWITCHES=1` and `FLUTTER_ENGINE_SWITCH_1=enable-dart-profiling=false`. Compare medians from each process and report their range. Preserve the output checksums and binary/source hashes with the raw reports.

The fixtures enter through production `ChatChannel.fromJson` and the real `ChatController`, with fake network and credential hosts. The 175-channel case has 100 public channels and 75 direct messages. Cases include empty overviews, four unread threads in one fifth of channels, 32 threads in every channel, and a separate 256-thread stress case. The 1,000-channel case exceeds ordinary response caps and is a stress test. Five warmup bursts precede seven measured bursts of 40 notifications. Each notification runs a listener that obtains and consumes the inbox projection. Preview bursts also replace 40 canonical Store records. An independent sort and unread filter verify the expected ID order before timing; callback checksums verify consumption during timing.

Set `CHAT_DERIVED_PROFILE=1` and `FLUTTER_ENGINE_SWITCH_1=enable-dart-profiling=true` for a separate diagnostic process. It captures direct hot-query CPU samples and, when the runtime supports allocation tracing, map-iterator allocations during unchanged, preview, and last-viewed changes. Exclude diagnostic-process timings from comparisons. Direct-query CPU samples describe the projection rather than notification dispatch. Allocation records cover only traced map iterators, not total heap allocation.

The result measures warmed macOS profile AOT controller/projection work. It excludes network latency, widget construction, layout, rendering, physical mobile performance, and frame rate. Newly received overview maps still require a copy and initial summary calculation. Changed last-viewed cutoffs require a fresh count. Raw mutable constructor maps retain live scans for compatibility.
